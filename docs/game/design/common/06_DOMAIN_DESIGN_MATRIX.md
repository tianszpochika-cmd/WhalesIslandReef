# 全领域设计矩阵

本文件回答一个问题：每个领域从“只有想法”到“可以交给制作和开发”的 0→1，必须留下哪些设计成果。玩法目录是第 16 个横向领域，负责把各系统串成玩家循环。

这里的“第一版设计完成”不等于美术资源、代码、数值表和全部内容已经制作完成。它表示：目标、边界、核心数据、状态变化、依赖关系、验收方式已经明确，后续可以拆成 D 级开发任务。

## 2. 每个领域必须达到的 0→1 交付物

每个领域至少要有以下 8 项，缺一项就只能算“概念完成”：

1. **目标**：玩家能感知到什么，为什么值得存在。
2. **内容边界**：做什么、不做什么，避免无限扩张。
3. **数据定义**：实体、字段、枚举、ID 和版本。
4. **状态机**：正常、受损、失败、恢复、终局等状态如何变化。
5. **系统权属**：谁能写入数值，Agent、玩家和 NPC 分别只能做什么。
6. **跨域事件**：哪些事件会触发其他系统变化。
7. **表现要求**：画面、声音、交互和反馈的最低标准。
8. **验收用例**：至少有正常路径、异常路径和存档/读档路径。

## 3. 统一制作层级

| 层级 | 交付物 | 例子 |
|---|---|---|
| L0 规则 | 约束和裁决公式 | 风暴会降低能见度；船舶系统裁决航速 |
| L1 原型 | 一个可操作闭环 | 一艘船驶离一个港口并安全返航 |
| L2 垂直切片 | 多系统联动样例 | 船员、天气、贸易、任务和战斗同时工作 |
| L3 内容扩展 | 批量内容和变体 | 50 岛、300 动物、200 道具 |
| L4 上线质量 | 性能、存档、兼容、本地化 | Steam 目标平台的完整验收 |

## 4. 实际开发顺序

```text
common 规则冻结
  ↓
ship + environment + islands 形成航行世界
  ↓
character + factions + economy 形成社会关系
  ↓
items + buildings 形成生产与港口服务
  ↓
combat + quests 形成可重复玩法
  ↓
ui + audio + presentation 形成可游玩的反馈
  ↓
批量内容、性能、存档、本地化和发布验收
```

## 5. 现阶段结论

- 船舶不再是单个大文档，而是独立目录中的 11 个专题文档。
- 其他 14 个系统领域和新增 gameplay 横向领域已经拥有第一版专题文档和目录入口。
- 下一阶段不是继续无限增加清单，而是选一个“港口—船—海域—船员”的垂直切片，把这些设计真正串起来。
- 批量数量是内容目标，不是当前已制作数量；制作时必须从小规模样例开始，再扩展到目标总量。
